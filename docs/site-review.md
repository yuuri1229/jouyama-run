# サイト改善レビュー（デザイン／システム）

対象：`niigata24h-run.com`（Next.js 14 静的エクスポート → GitHub Pages）
実施：2026-09-05

このドキュメントは、サイト全体を「デザイン」「パフォーマンス」「アクセシビリティ」
「情報設計・運用」の4面から点検した結果と、実施済み／未実施の改善内容をまとめたものです。

---

## 総評

デザインの方向性そのものは良く出来ています。緑を「線・数字・アクセント」に限定し、
濃色ベタをヒーロー／ENTRY／フッターの3箇所に絞る方針は一貫していて、
写真の力を殺さずに大会の性格（時間走＝淡々と積み上げる競技）を表現できています。
タイポグラフィのスケールや行長（`--measure`）を変数で定義している点も、
個人運営のサイトとしては水準が高いです。

一方で、**「見た目の完成度」に対して「配信の作り」が追いついていない**のが最大の課題でした。
特にアイコンフォントを丸ごと配信していた件は、デザインの良さが初回訪問者に届く前に
体感速度で損をしていた状態です。また、大会の日時・料金がテンプレート内に直書きされており、
実際に**12時間走の制限時間が誤った日時で公開されていました**。

## 1. 致命度の高い問題（対応済み）

### 1-1. アイコンフォントを全アイコンぶん配信していた（2.3MB）

```
変更前: 2,344,316 bytes  （Material Symbols 可変フォント全体）
変更後:    19,952 bytes  （実際に使う31アイコンのみ）
削減率:      99.1%
```

`@import url(".../Material+Symbols+Outlined:...")` は、指定しない限り
**全アイコン入りの可変フォントを丸ごと**返します。このサイトが使っているのは31個だけです。
Google Fonts の `icon_names=` パラメータでサブセットを要求するように変更しました。

使用アイコンは `lib/assets.js` の `MATERIAL_ICONS` で管理しています。
**アイコンを追加したときは、このリストにも名前を足してください**（足し忘れると豆腐になります）。

あわせて `display=block` を明示しました。これが無いと、フォント到着前に
`campaign` `chevron_right` `arrow_outward` といった**英単語が生のまま画面に出ます**。

### 1-2. フォントCSSを `@import` で読んでいた

`@import` は「globals.css を読み終えてから、はじめてフォントCSSを取りに行く」直列処理になり、
描画開始が1往復ぶん遅れます。`app/layout.jsx` の `<link>` に移し、
`preconnect`（fonts.googleapis.com / fonts.gstatic.com）も追加しました。

### 1-3. ヒーロー写真4枚（約2.7MB）を初回表示で同時取得していた

4枚すべてを `background-image` 付きで DOM に置いていたため、
1枚目が出るべきタイミングで残り3枚が帯域を奪い合っていました。

```
変更前: 2,707KB（hero-1〜4 を同時取得）
変更後:   331KB（hero-1 のみ。2枚目以降は切り替わる直前に取得）
```

1枚目は `<link rel="preload" as="image" fetchpriority="high">` で先読みします
（CSS背景画像はCSS解析後にしか取得が始まらないため、LCPに直接効きます）。

### 1-4. JavaScriptが動かないと本文が真っ白になる

`.reveal`（スクロール表示演出）の初期状態が `opacity: 0` で、
救済用の `.no-js .reveal` ルールはあるものの、**`no-js` クラスを付ける処理がどこにも無い**
状態でした。JSの読み込み失敗や無効化で、ヒーロー以外の全セクションが見えなくなります。

`<noscript>` によるスタイル上書きと `@media (scripting: none)` の二重で救済しました。

### 1-5. 12時間走の制限時間が誤っていた（情報の誤り）

```
変更前: 制限時間：11月22日(日)0時、11月23日(祝)12時
```

デイスタートは 11/22 12:00 発走なので、制限時間は **11/23 0:00** です。
「11月22日(日)0時」はスタートより前の時刻で、明らかな誤りでした。
種目カードを「スタートと制限時間をセットで示す」形に組み直しています。

```
変更後: デイスタート：11月22日(日)12時（制限時間 11月23日(祝)0時）
        ナイトスタート：11月23日(祝)0時（制限時間 11月23日(祝)12時）
```

タイムバンド右端のラベルも、デイの帯なのに「ナイトスタート」と書かれていたため
「制限時間」に修正しました。スケジュール表も、23日0:00 の行が
「ナイトスタート／デイスタートの制限時間」であることを明示し、
直後の「0:30 賞品授与」が何の授与か分かるようにしています。

### 1-6. Googleアナリティクスがページビューを二重計上していた

`gtag('config', ...)` を初期化スクリプトと `useEffect` の両方で呼んでいたため、
**すべての初回訪問が2PVとして記録されていました**。初期化側を
`send_page_view: false` にし、送信を `useEffect` の1箇所に集約しました。

> ⚠️ これまでのGA4の数値は、セッション数に対してPVが約2倍に膨らんでいます。
> 過去データと比較する際はご注意ください。

## 2. 情報設計・運用（対応済み）

### 2-1. 大会情報の単一ソース化 — `lib/event.js` を新設

開催日・エントリー期間・参加費・定員・周回距離が
`app/page.jsx` / `app/layout.jsx`（JSON-LD） / `components/Hero.jsx` に
**それぞれ別の文字列として直書き**されていました。1-5 の誤りはこの構造が原因です。

`lib/event.js` に「事実」を集約し、表示用ラベル（`2026年11月22日(日)` など）は
日時から自動生成する形にしました。**毎年の更新は原則このファイルだけ**で済みます。

```js
race12: {
  day:   { startAt: jst("2026-11-22T12:00:00"), finishAt: jst("2026-11-23T00:00:00") },
  night: { startAt: jst("2026-11-23T00:00:00"), finishAt: jst("2026-11-23T12:00:00") },
  fee: 5500,
}
```

曜日はJST基準で判定し、祝日だけ `HOLIDAYS` で `(祝)` に差し替えています。

### 2-2. 「エントリー受付中」が固定文字列だった

`エントリー受付中｜2026年11月13日(金)まで` が直書きで、
**締切を過ぎてもサイトが「受付中」と言い続ける**状態でした。
`entryStatus()` が受付前／受付中／受付終了を日付から判定し、
文言とボタンの出し分けを行います。

静的サイトなので判定はビルド時刻基準です。締切当日に自動で切り替わるよう、
デプロイワークフローに**1日1回の再ビルド**（毎朝5時 JST）を追加しました。

### 2-3. ビルドの再現性

`package-lock.json` が未コミットで、CIも `npm install` でした。
`next: ^14.2.5` は浮動なので、**ある日突然デプロイだけ壊れる**構成です。
ロックファイルをコミットし、CIを `npm ci` ＋ `cache: npm` に変更しました。

### 2-4. microCMS の取得回数

`getNewsItems()` がトップ・一覧・記事ページ・`generateStaticParams` ・
`generateMetadata` ・sitemap から個別に呼ばれていました。
React の `cache()` で包み、1ビルド1回に集約しています（記事数が増えるほど効きます）。

> **訂正（2026-10）**：`cache()` は「1回のレンダリングの中」でしか効かず、実際には
> ページごとに取得し直していました（障害時のログが1ビルドで7回出ていた）。
> モジュール単位のメモ化に改めています（→ 第6章）。

## 4. デザインシステム（一部対応済み）

### 対応済み

- **余白スケールの導入**：`--space-2xs` 〜 `--space-3xl` を定義。
  これまでセクションごとに `clamp(60px, 7vw, 104px)` のような値を都度書いていたため、
  似て非なる余白が増えやすい構造でした。
- **流体タイポの役割化**：`--fs-lead` / `--fs-h3` / `--fs-h2` / `--fs-display` を追加し、
  同じ `clamp()` が複数箇所に重複していた部分を置換。
- **DOM順依存セレクタの排除**：`.race-card:nth-child(2)` → `.race-card--12`、
  `.mobile-nav > a:last-of-type` → `.mobile-nav-cta`。
  カードの並び順を変えると配色が入れ替わる、という壊れ方を防ぎます。
- **`text-rendering: optimizeLegibility` を削除**。和文で得るものが無く、
  長文で描画コストだけ増える指定です。
- **未使用ウェイトの削除**：Zen Kaku Gothic New の 900、Oswald の 500 は未使用でした。
- **`manifest.webmanifest` を追加**。`icon-192.png` / `icon-512.png` が用意されているのに
  どこからも参照されておらず、ホーム画面追加時のアイコンが効いていませんでした。
- **パンくずの構造化データ**（`BreadcrumbList`）を最新情報ページに追加。
- **`SportsEvent` の JSON-LD を補強**：`price` / `priceCurrency` が無く
  Googleのイベント リッチリザルトの要件を満たしていませんでした。
  種目ごとの `Offer` に分け、住所も `streetAddress` / `postalCode` まで記述。

### ヒーロー写真の切り替えが不安定だった件（調査と修正）

「背景画像の推移の挙動が少し不安定」との指摘を受けて調査。原因は3つあり、
うち2つは遅延読み込みを入れたときの退行でした。

**原因1：画像の取得が「表示する瞬間」まで始まらない**

`<img>` を挿入すると同時に `is-active` を付けていたため、
ダウンロードの開始と「表示中」になるのが同時でした。写真が届くまでの間、
背景の暗緑 `#071f0b` が見えます。

**原因2：新しい写真にフェードインがかかっていない**

挿入と同時に `is-active` が付くと、CSS transition に必要な「変化前の値」が
存在しません。DOM挿入の瞬間を計測すると `opacity=1`、1フレーム後も `opacity=1`。
`transitionstart` が発火するのは古いスライド（1→0）だけで、
古い写真が1.4秒かけて消える下で、新しい写真は瞬間的に点灯していました。

**原因3：ホバーとタップで自動送りが不安定になる**

- `useEffect` の依存に `current` と `paused` があり、`setInterval` が
  作り直されてカウントが0に戻っていた。ヒーローは画面全体を覆うため、
  マウスが乗っているのが常態で、1秒触れただけで次の切替が4.5秒→9.0秒に
- スマホでドットをタップすると `mouseenter` と `focusin` が合成発火する一方、
  `mouseleave` / `focusout` はヒーロー外をタップするまで来ない。
  実測でタップ後14秒間、自動送りは0回（＝事実上停止）

**修正**

1. 次の1枚を先読みする（`window.load` 後に開始し、初回表示1枚は維持）。
   読み込みが済んでいない写真には切り替えない
2. 先読みで既にDOMにあるため `opacity: 0 → 1` の遷移が成立し、フェードインが効く
3. `setInterval` は一度だけ生成。停止・再開はハンドラ内で制御
4. ホバー停止は操作部（`.hero-foot`）に限定し、`pointerType === "mouse"` のときだけ。
   キーボードは `:focus-visible` で判定してタップの合成フォーカスを除外
5. `visibilitychange` でタイマーを停止・再開し、タブ復帰時に位相を揃える
6. 直前の写真を `.is-prev` で不透明のまま下に残す。新旧を同時に半透明にすると
   重なりの隙間から背景が透けるため

実測（切替の瞬間に写真が届いていない時間）:

| 回線 | 修正前 | 修正後 |
|---|---|---|
| Slow 3G (400kbps) | 3938 / 3712 / 3368ms | **0ms** |
| Fast 3G (1.6Mbps) | 1019 / 959 / 886ms | **0ms** |
| `transitionstart` の発火 | 古い方のみ | **新しい方（フェードイン）も発火** |
| 写真の上にマウスを乗せたとき | 次の切替が4.5秒→9.0秒 | **影響なし（5.0秒間隔を維持）** |
| スマホでドットをタップした後 | 自動送り0回／15秒 | **3回／15秒** |

### タイムバンド（昼→夜→朝の帯）の色が時刻と合っていなかった件

種目カードの帯は、停止位置をCSSに直接書いていました。実際の日の入り・
日の出（新潟市西蒲区／2026-11-22は日の入16:29・薄明終了16:58、
翌朝は薄明開始06:04・日の出06:33）と照合すると、2〜6時間ずれていました。

| 帯 | 本来の位置 | 旧CSSの位置 |
|---|---|---|
| 24時間走：完全な夜になる | 20.7%（16:58） | 48%（23:30） |
| 24時間走：日の出 | 77.3%（06:33） | 84%でまだ暗い緑、昼は100%（12:00） |
| 12時間走デイ：完全な夜 | 41.3%（16:58） | 100%（24:00）＝約6時間ぶんのずれ |
| 12時間走ナイト：完全な昼 | 約58%（07:00過ぎ） | 100%（12:00）＝夜明けが5時間に引き伸ばされていた |

色そのものにも問題がありました。橙 `--day #c98a1e` から紺
`--night #123049` へ直接グラデーションすると中間が `#6d5d33` の
濁ったオリーブになります。旧CSSの中継色 `#7a6a2a` `#4a5c2c` `#6b6b3a`
`#2f4a3a` はいずれも緑寄りで、夕焼け・朝焼けに見えていませんでした。

**修正**：`lib/sky.js` を追加し、帯の色を実時刻から組み立てるようにしました。

- 太陽時刻（薄明開始／日の出／日の入／薄明終了）を会場の緯度経度で算出して保持
- 空の基準色を「日中 → 斜光 → 地平線 → 薄明(菫) → 夜 → 真夜中」の6段で定義。
  紫を経由させることで、混色で緑が出るのを防ぐ
- `skyGradient(開始, 終了)` が任意の時間帯のCSSグラデーションを生成する

3本の帯はすべて同じ関数から作られるので、開催日を動かしても
（`SUN` に新しい日の太陽時刻を足せば）自動で追従します。
描画結果をピクセル単位で検証し、16:29＝橙、16:58＝菫、18:00＝紺、
00:00＝最暗、06:33＝橙、08:12以降＝昼 になっていることを確認しています。

### 写真のWebP化・レスポンシブ配信

`npm run images`（`scripts/build-images.mjs`）で、元の `.jpg` を残したまま
幅ちがいの `.webp` を書き出します。ページ側は `<picture>` で出し分けます。

```
WebP対応ブラウザ → 画面幅に合った軽い .webp
非対応ブラウザ   → もとの .jpg（元写真は消していないので安全）
```

ヒーローはCSSの `background-image` をやめて `<img>` に変更しました。
背景画像は画面幅に応じた出し分け（`srcset`）ができず、
**スマホにも1920px幅の写真を配っていた**ためです。
見え方は `object-fit: cover` / `object-position: center 45%` で従来どおりです。

品質は78ではなく **68** を採用しています。元写真が粒状（高感度）で
WebPが不得意な素材のため、78のままだと元のJPEGとほぼ同サイズでした。
ヒーローは暗いスクリムと文字が重なる面なので、68でも劣化は判別できません。

実測（ブラウザで実際に取得されたファイル）：

| | 変更前 | 変更後 |
|---|---|---|
| ファーストビューの写真（デスクトップ 1440px） | 331KB | **109KB** |
| ファーストビューの写真（スマホ 390px） | 331KB | **62KB** |
| ページ全体の写真（デスクトップ・最後までスクロール） | 約3,900KB | **822KB** |
| ギャラリー4枚（デスクトップで実際に届く幅） | 1,083KB | 184KB |

> ⚠️ **写真を差し替えたら `npm run images` を実行してから**コミットしてください。
> 実行を忘れると、新しい写真の `.webp` が無いため
> 古い `.webp` が表示されたままになります。

### ヒーローの暗幕・構図・文字の再設計（2026-10）

背景の暗幕が弱く、写真の上に文字がそのまま載っていた。ヒーロー文字の背後にある
**実際の描画ピクセル**（文字だけ透明にして撮影）から、スライド4枚×画面幅4種で
白文字のコントラストを測った（大きい文字は3:1、小さい文字は4.5:1が基準）。

| 画面 | 変更前の主な不足 |
|---|---|
| PC 1920 / 1440 | 「12」2.2〜2.8、「時間走」1.1〜2.6、「TIMED RUN」1.6〜2.8、リード文3.7〜4.2 |
| タブレット 768 | スライド3でリード文2.0、「TIMED RUN」1.7〜2.6 |
| スマホ 390 | ほぼ合格（下半分の暗幕が強い） |

**変更後：基準未達は、スマホのスラッシュ「/」1件のみ**（装飾の記号で `aria-hidden`。
影で縁を立てて視認性は確保）。

設計の要点：

- **暗幕は黒ではなくサイトの深緑 `#071f0b`**（ヒーロー地色・フッターと同色。
  `--ink-rgb`）。緑 `--pine` を重ねると写真が緑がかる（過去の退行）ため使わない。
- **暗幕の中心を「画面の左端」ではなく文字ブロックの位置に置いた。**
  PC幅では文字が中央寄せのコンテナに載る（1920pxなら左端から372px）。
  左端基準だと、文字のない左の余白ばかり暗くなり、写真の上半分まで沈んでいた。
  文字のない領域の明るさは、暗幕なしの比で **左上 20%→77%、右上 66%→84%**。
- **写真ごとに構図（`object-position`）を指定**（`components/Hero.jsx` の `SLIDES`）。
  hero-2 は被写体が中段の一列、下は無地の路面なので下寄せにして、
  「ランナーは上、文字は路面の上」という配置にした。
- 琥珀は暗い地色用の `--day-on`（`#e8ac3f`）を新設。`--day`（`#c98a1e`）は
  白地では2.9:1しかなく、明るい写真の上では溶けていた。
- ゴーストボタン・日付チップ・下端の帯は、暗幕と同じ深緑の下地にそろえた。
- `calc()/max()` を使う宣言を解釈できない古いブラウザ向けに、簡易な暗幕を先に置いてある。

### 未対応（判断が必要なもの）

**A. ヒーローの高さ指定（`dvh`）**

現在 `min-height: calc(100dvh - var(--header-h))` です。`dvh` は
スマホのアドレスバー開閉で値が変わるため、**スクロール中にヒーローが伸縮**します。
`svh` にすると高さは安定しますが、バーが隠れたときに下に隙間が出ます。
どちらを取るかは好みの問題で、現状の選択も妥当です（体感が気になる場合のみ変更を推奨）。

**B. Next.js のバージョン**

`14.2.35` で動作しています（14系の最新）。`npm audit` は Next.js（critical）と
その依存の postcss（high）を報告し、修正は 16.3.x へのメジャーアップグレード
（React 19 への更新を含む）でのみ提供されています。
報告された内容（Image Optimizer、Server Components、Server Actions、middleware、
rewrites、CSP nonce 等）は、このサイトでは**使っていない機能**です。静的エクスポートで
サーバーを持たず、`images: { unoptimized: true }`、`afterInteractive` のスクリプトのみ。
postcss の指摘も、ビルド時に自前のCSSを処理するだけで、外部入力は通りません。
したがって**実害のある脆弱性は確認していません**が、依存の鮮度としては更新が望ましいため、
別作業（ビルド・見た目の全面確認つき）として切り出しました。

## 6. 2026-10 の改善（実測ベース）

ビルドした成果物を実ブラウザ（Chromium）で、5つの画面幅（390/768/1024/1440/1920）×
3ページ（トップ・ニュース一覧・記事）で計測し、見つかった問題を直した。
計測はヘッドレスChromiumのみで、実機（特にSafari）は未確認。

### A. 不具合と基準未達

- **コースの「960m／周」の行高が `.9` ではなく `1.9`**：`.course-info > p` の詳細度が
  `.course-stat` を上回り、行高と余白を上書きしていた（数字の上下に約90pxの空き）。
- **ヒーローが `<main>` の外**：h1・ボタンがどのランドマークにも属さなかった（axe の region 違反 4〜11件→0）。
- **アイコンのサイズ指定が効いていなかった**：Googleが配信する CSS にも
  `.material-symbols-outlined { font-size: 24px }` があり、**自前CSSより後に読み込まれる**ため、
  同じ詳細度の基準ルールが負けていた。個別の指定だけが効き、17.25〜19.55px の小数サイズが
  10種類混在していた → `span.material-symbols-outlined` で詳細度を上げ、**16/20/24px の3段**に。
- **尺度の整理**：文字サイズ（小数サイズを廃止、12px未満なし、本文16px）、字間（17→5段+負値）、
  行高（本文系を2段、見出し1段）を `:root` のトークン（`--fs-*` `--ls-*` `--lh-*` `--icon-*`）に集約。
- **タップ領域**：ヘッダーのナビ・SNS・ロゴ、フッター、パンくず等を、見た目を保ったまま
  **実際に反応する範囲44px以上**に（`elementFromPoint` で実測。text-arrow は見た目32px→反応47px）。
- 昼の琥珀アイコンが白地で2.94:1 → 濃い `--day-d`（5.1:1）。
- スケジュール表の時刻列を44%幅から固定幅に。

### B. TOPのUX

- ヒーローに**受付状況・締切・開催までの日数**（以前はENTRYまでスクロールしないと不明）。
- 写真の自動切り替えに**一時停止ボタン**（WCAG 2.2.2）、ドットを36×44px、スマホは**スワイプ**。
- **スマホの固定エントリーバー**（受付中のみ。ヒーロー・ENTRY・フッターが見えている間は隠す）。
- ルールを `<details>` の**アコーディオン**に（本文は変更なし。印刷時は全開）。
- **スケジュール表を `lib/event.js` の `SCHEDULE` に移した**（日付が `page.jsx` に直書きで、
  `EVENT` を動かしても表だけ古いままになる構造だった。表示テキストは変更前と完全一致を確認）。
- ニュースが2件以下のときの余白を圧縮。

### C. システム

- **microCMS が落ちると、記事が消えたサイトが公開されていた**：APIキーがあるのに取得できないとき、
  黙ってサンプル記事（1件）にフォールバックして**ビルドが成功**していた。毎朝5時の自動ビルドが
  一時障害に当たると、そのまま本番に出る。→ **ビルドを失敗させ、公開中のサイトを残す**。
  通信エラー・5xx・429 は3回まで再試行（1秒→3秒）、401/403/404 は即失敗。
  100件を超える記事も全件取得（以前は101件目以降が黙って切れていた）。
  ロジックは `lib/paginate.js` に切り出し、取得回数・再試行・即失敗・重複なしを単体で検証した。
- **SNS共有**：ニュース一覧・記事ページに `og:image` / `og:url` / `og:site_name` / `og:locale` が無く、
  `twitter:card` も `summary` だった（Next.js は `openGraph` を親と**マージせず丸ごと置き換える**ため）。
  `lib/seo.js` の `pageMeta()` に統一。
- **構造化データ**：`SportsEvent` が全ページ（404・記事含む）に出ていたのをトップだけに。
  `availability` が常に `InStock`（締切後も）だったのを、受付前/中/終了で
  `PreOrder`/`InStock`/`SoldOut` に。日時をUTC表記から `+09:00` つきに。
  JSON-LD に埋める文字列の `<` をエスケープ（記事タイトルは microCMS 由来のため）。
- **締切後の自己矛盾**：ENTRYだけが「受付終了」になり、ヒーロー・ヘッダー・フッターは
  申込フォームへ誘導し続けていた → 受付終了後は自動でエントリーリストへの導線に切り替わる
  （締切を過去にした複製でビルドして全箇所を確認）。
- 404ページを日本語に（以前は英語の既定文面）。
- **PRにビルド確認**（`pull_request` で build のみ。公開は main だけ）。
  concurrency のグループを分け、PRのビルドが公開ジョブを取り消さないようにした。
- 確認して**問題なかったもの**：GA4 の初回 `page_view` はちょうど1回（二重計上の修正は有効）。
